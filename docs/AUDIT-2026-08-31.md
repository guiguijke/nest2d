## §P — Python : pass structurel & finalisation

### P-1 — CRITIQUE : le lattice ignore les rotations permises — pièces livrées dans des orientations interdites (miroir Python + JS)

- **Fichiers** : `workers/nesting/core/structure.py:135` (détection),
  `:401-410` (`small_lattice`), `:590` (`deg0 / deg0 + 180`),
  `:535` (`_lattice_rotated` : `deg + 90`) ; `plan_lattice` pose le rect à
  rotation `0.0` sans validation (`:230`). Miroirs :
  `app/composables/structureClient.js:449-451` (même filtre) et `:338`
  (`attachRings` : `deg0 : deg0 + 180`).
- **Problème** : la détection vérifie que les rotations demandées SONT des
  quarts de tour, mais jamais que les rotations **posées** par le lattice
  (0/180 en zigzag, +90 en variante tournée) sont **permises**.
- **Scénario** : `rotationCount=1` → l'UI sert `rotations=[0]`
  (`nest.post.js:60-64`). Détection acceptée (`[0] ⊂ {0,90,180,270}`), le
  sous-solve moteur respecte `allowed_orientations=[0]`, mais le lattice
  (posé en premier, tout-ou-rien, `structure.py:742-750`) place la moitié des
  fillers à **180°** — pièce asymétrique retournée. L'alternative grille est
  rang 0 (`grid: -1`, `main.py:1485`) : c'est la vue par défaut du modal.
- **Impact** : non-conformité silencieuse du livrable de découpe (fil du
  matériau, sens décoré) sur le cas d'usage produit phare, **des deux côtés**
  (serveur ET navigateur).
- **Fix** : passer les rotations permises à `small_lattice` et ne générer que
  les variantes dont toutes les rotations posées sont permises ; exiger
  `0.0 ∈ rect["rotations"]` dans `detect_structural_case` sinon repli moteur.
  Miroir JS identique.

### P-2 — MAJEUR : `plan_lattice` ne vérifie pas que la grille tient dans la tôle — pièces hors tôle livrées rang 0

- **Fichiers** : `workers/nesting/core/structure.py:218-233` (`cols =
  n_full + (1 if remainder else 0)`, aucune borne `cols * pitch_x` vs
  `sheet_w` ; idem `lattice_top` en objectif y vs `sheet_h`).
- **Preuve** (vérifié calculatoirement) : 310 lattes 510×10 + 100 carrés
  8×8, tôle 1000×2000, space 1 → `per_col=181`, `cols=2`, colonne 2 à
  x ∈ [512, 1022] → **129 pièces à 23 mm hors tôle**. La zone B devient un
  rectangle inversé (zw < 0 → silencieusement vide, `_zone_solve:287`), la
  garde `STRUCT_TOL` (`main.py:1200` : struct_w ≤ best_w × 1,2) laisse
  passer, `verify_layout` pose `insideSheet=False` (`metrics.py:361`) mais
  ce n'est qu'un badge — l'alternative est exportée et triée en tête.
- **Fix** : `return None` si `cols * pitch_x + space > sheet_w` (resp.
  lignes vs `sheet_h` en −Y) ; complément P-4.

### P-3 — MAJEUR : bbox de mesure de la zone B′ transposée — rotation +90° appliquée à une instance transposée à −90° (miroir Python + JS)

- **Fichiers** : `structure.py:729-730`
  (`bbox=(-sy1, sx0, -sy0, sx1)` = bbox de R(+90°)) alors que l'instance de
  solve est `T(-90)·coords` (`main.py:1133` : `[[y, -x] …]`) — la bonne bbox
  est `(sy0, -sx1, sy1, -sx0)`. Miroirs : `structureClient.js:793-796`
  (`transposedBbox`) vs `localJobPrivate.js:125` (même signe faux).
- **Conséquence** : le check anti-débordement `used_w <= solve_w + 1e-3`
  (`structure.py:303`) mesure un bord imaginaire ; écart = 2×ordonnée du
  centroïde d'origine (33,6 mm sur le fan de test à rot 0). En job −Y, la
  bande du haut peut réellement déborder la tôle après map-back — le garde
  censé l'attraper regarde ailleurs. Le map-back lui-même est correct
  (vérifié : `M(G) = R(r)·coords + T(+90)·t + c`).
- **Fix** : bbox de R(−90°) des deux côtés ; ajouter un test qui dérive la
  bbox comme `main.py` et vérifie le rejet d'un débordement réel (le test
  existant `test_zone_solve_transposed_map_back` passe une bbox ad hoc et ne
  verrouille pas cette cohérence).

### P-4 — MAJEUR : aucun garde bloquant sur `insideSheet` à la finalisation

- **Fichiers** : `main.py:1386-1400` (`_finalize_alternative` ne rejette que
  `n != total_requested_count`) ; `metrics.py:361-362` (badge non bloquant).
- **Lecture** : les gardes du pass protègent le NOMBRE de pièces, jamais
  leur position. `verify_layout` calcule déjà le bon verdict (`sheet.covers`)
  mais il n'entre dans aucune décision — P-2/P-3 franchissent donc toute la
  chaîne jusqu'au DXF rang 0.
- **Fix (3 lignes)** : dans `_finalize_alternative`, repli moteur si
  `verification["insideSheet"]` est faux pour une alternative `structural`.
  C'est le filet commun qui transforme chaque futur bug géométrique du pass
  en repli propre. **Priorité n°1 recommandée.**

### P-m — Mineurs Python

1. **`rotations: []` interprété 3 façons** : `main.py:471` (`or [0.0]`),

   `structure.py:134` (`or [0,90,180,270]`), le JS rejette
   (`structureClient.js:450`). Le serveur `JSON.parse` sans valider
   (`nest.post.js:103`). Fix : normaliser `[]` → `[0.0]` à l'entrée +

   `tx + bx0 >= -1e-3`.
3. **`LATTICE_SIMPLIFY_MM` codé dur 0,05** (`structure.py:75`) alors que

   `space + 2 × SIMPLIFY_MM` depuis la même source.
4. **Budget temps du pass non borné globalement** : zones × tronçons ×

   (magnitude multi-tronçons non documentée au §F.4). Fix : deadline mur
   passé à `build_structural_layout`.
5. **Rétention mémoire des caches DXF** : `dxf_document_cache` vidé au début
   du job SUIVANT (`main.py:349/397`) — le doc ezdxf du job N−1 reste en RAM
   pendant tout l'idle worker. Fix : vider en `finally` de `nesting_process`.
6. **`_shoelace` inexact sur anneau ouvert** (`structure.py:79-83`, segment
   de fermeture manquant) — le miroir JS `polygonArea`
   (`localJobPrivate.js:142-150`) gère la fermeture circulaire. Bénin
   (détection/caps légèrement décalés).
7. **`count` non-entier non validé** (`nest.post.js:56/103` — pas de
   `Number.isInteger`, contrairement aux sheets :160) → erreur de
   désérialisation Rust peu actionnable. Fix : `Math.floor` + rejet < 1.
8. **Fenêtre d'annulation non protégée pendant la finalisation** : aucun
   `should_cancel` entre la fin du solve/du pass et l'écriture finale
   (`main.py:1034→fin`) — une annulation pendant reveal/build (~2-15 s)
   finalise en `done` sans refund. Fix : re-check avant l'écriture.

## §Q — Rust : moteur (nest-engine / sparrow / jagua-rs)

### Q-1 — MAJEUR : pre-check de faisabilité trop laxiste d'un espacement complet → panique SPP (reproduite)

- **Fichiers** : `workers/nesting/core/main.py:479` + miroir
  `app/composables/localPayloadBuilder.js:577` (les gardes) ; panique dans
  `sparrow/src/optimizer/lbf.rs:74`.
- **Preuve** : les gardes comptent `w + space <= sw` alors que jagua inflate
  `space/2` **de chaque côté ET sur le conteneur**
  (`jagua-rs/src/io/import.rs:37`) — la condition réelle est
  `w + 2·space <= sw`. Reproduction CLI (vérifiée) : strip 10, pièce 8×8,
  `min_item_separation: 2` → le garde passe (8+2≤10), jagua exige 12 →
  élargissement ×1,2 en boucle →
  `panicked at lbf.rs:74: strip-width is running away`.
- **Scénario produit** : pièce quasi ajustée (998 mm sur tôle 1000, space 2)
  — le cas « demande exacte » est un scénario assumé. En SPP,
  `panic = "abort"` (Cargo.toml:28) tue le worker natif ; le Web Worker
  navigateur meurt sur la même panique. Les deux chemins d'erreur aval sont
  propres (natif : `engine.py:160` → EngineError avec stderr ; wasm : pool
  tolérant), donc le coût est un **crash déterministe avec message Rust
  brut** au lieu de « Part(s) too large for the sheet ». En BPP la même
  fenêtre dégrade proprement (`unplaced > 0` → merge → infeasible) — seul
  le SPP panique.
- **Fix** : `w + 2*space <= sw + 1e-6 && h + 2*space <= sh + 1e-6` dans les
  deux gardes ; en durcissement, convertir l'assert `lbf.rs:74` en erreur
  remontée comme événement.

## §R — UI : orchestration locale, état, UX

### R-1 — CRITIQUE : quota free consommé SANS refund sur les échecs de validation postérieurs à la consommation

- **Fichiers** : `server/api/project/[slug]/nest.post.js:297` (charge
  `assertCanNest`) → `:303` (`validateDirections` 403) / `:366-378`
  (409 `concurrent_limit`) / `vault_locked` levé dans
  `enqueueNestingJob` — `server/utils/entitlement.js:452-460`.
- **Preuve** (vérifiée) : `$inc: { freeNestingUsed: 1 }` atomique dès :297 ;
  le 409 `concurrent_limit` (compte pending/processing/awaiting_local) est
  jeté après, sans compensation — le refund n'existe que via le champ
  `charge` du doc job, or aucun job n'est créé. Le commentaire
  « Consumes a unit only once the request is fully validated »
  (`entitlement.js`) est contredit par l'ordre d'exécution.
- **Scénario** : utilisateur Free (1 job parallèle), reclique « Imbriquer »
  pendant qu'un calcul tourne ou double-clique (cf. R-2) → 409 → **1 unité
  gratuite sur 10 perdue, sans job, sans message, sans refund**. Un vault
  verrouillé brûle aussi une unité.
- **Fix** : déplacer `assertCanNest` après TOUTES les validations, ou
  décrémenter `freeNestingUsed` en compensation sur ces trois sites quand
  `charge.type === 'free'`.

### R-2 — MAJEUR : « Imbriquer » sans garde de double soumission, erreurs avalées, bouton désactivé sur échec

- **Fichiers** : `app/composables/files.js:453-511`.
- **Preuve** : pas de verrou in-flight pendant le POST ; le `catch` interne
  ne `return` pas pour les erreurs non listées (409, 500…) → l'exécution
  continue vers `state.lastParams = state.requestBody` (:507) alors que le
  POST a échoué.
- **Scénario** : (a) double-clic pendant la latence → 2 requêtes peuvent
  passer le compteur de concurrence → 2 jobs + 2 unités chez un Free, ou
  1 job + R-1 ; (b) 409/500 → rien à l'écran ET bouton grisé
  (`isNewParams` false) — le « bouton muet » dans une variante distincte de
  §M.3.
- **Fix** : désactivation pendant le POST (ref in-flight), `return`
  explicite dans le catch + message i18n (`nest.error.concurrent`).

### R-3 — MAJEUR : annulation d'un job local EN FILE = zombie + bandeau d'erreur mensonger

- **Fichiers** : `app/components/UserResultItem.vue:144-158` +
  `app/composables/localSolverRegistry.js:87-94, 138-161`.
- **Preuve** : le `cancelJob` du registre (retire de `state.queue`, marque
  `cancelled`) n'est câblé **nulle part dans l'UI** (seuls les tests).
  `cancelNesting` fait POST /cancel + `cancelPool(slug)` — or `cancelPool`
  ne voit que les pools lancés (`pools` Map) ; un job en file survit, et
  `pump()` ne filtre que `phase === 'cancelled'`.
- **Scénario** : Free, job A courant, job B en file ; annulation de B
  (serveur `cancelled` + refund) → A finit → `pump()` lance B →
  `local-payload` répond 409 (garde `awaiting_local`,
  `local-payload.get.js:38`) → registre passe B en `error` → bandeau
  « Le calcul local a échoué… réessayez » sur un job annulé par
  l'utilisateur ; spinner sur un job mort en attendant.
- **Fix** : câbler `localSolverRegistry.cancelJob` dans `cancelNesting`
  (il fait déjà file + pools), et/ou purger dans `pump()` les entrées dont
  le job serveur n'est plus `awaiting_local`.

### R-4 — MAJEUR : pool multi-walks — impasse définitive si le worker de merge meurt

- **Fichiers** : `app/composables/localPool.js:596-673` (`failSlot` +
  `checkAllSettled`).
- **Preuve** : `checkAllSettled` poste l'op `merge` à `survivors[0]` sans
  vérifier que son worker est vivant ni poser de timeout. Si ce worker
  crashe après son solve (`onerror` → `failSlot` : `slot.outcome` reste
  `ok:true`, worker `terminate()`), `failSlot` rappelle `checkAllSettled`
  qui re-poste le merge **au même worker mort** — `postMessage` sur un
  worker terminé est silencieusement droppé → `pool.settle` jamais appelé →
  promesse de `runPool` jamais résolue → `state.running` jamais décrémenté.
- **Scénario** : démo ×4/×8, trap wasm/OOM du worker 0 après un solve
  réussi → carte « Calcul en cours… » à l'infini, et chez un Free le slot
  unique du registre reste occupé à vie.
- **Fix** : timeout de garde sur l'attente du merge qui settle sur les
  survivants ; choisir un worker vivant ET `outcome` ok.

### R-5 — MAJEUR : registre — re-file d'un job en erreur → double run du même slug

- **Fichiers** : `app/composables/localSolverRegistry.js:51-70, 138-150`.
- **Preuve** : `entry()` réutilise l'entrée existante sans remettre `phase`
  à `queued` — un job re-filé après échec (phase `error`) reste hors du
  garde `[queued,running,done]` de `ensureJob` → un deuxième `ensureJob` le
  re-push → 2 entrées en file → `launch()` (qui ne refuse que `cancelled`)
  l'exécute deux fois en concurrence : 2× `local-payload`, 2× `runPool`
  sur le même slug (`pools.set` écrase le premier pool : terminaison et
  décompte faussés).
- **Scénario** : échec réseau du fetch `local-payload` (job serveur reste
  `awaiting_local`, phase registre `error`) → sortie/retour sur la page
  pendant qu'un autre job occupe le slot → duplicata en file. Effet
  additionnel : `phase` affichée reste `error` → pas de libellé « en attente
  d'un slot ».
- **Fix** : réinitialiser `phase='queued'` + vider `result/frame/error` à
  la re-file d'un job `error`.

### R-6 — MAJEUR : vue live locale re-figée — la couche registre casse la fenêtre d'égalité du champion (régression du fix B.4)

- **Fichiers** : `app/composables/localSolverRegistry.js:73-85`

- **Scénario** : (a) SPP local — phase 2 vit à corridor W₀+1 mm → toutes

### R-7 — MAJEUR : snapshots sessionStorage — réglages perdus au F5 sans navigation inter-projet préalable

## §S — Thèmes transverses

1. **Légalité du livrable vs nombre de pièces** (P-1→P-4) : les gardes du

   permises) ni la position (bords de tôle). Le filet final existe déjà —
   `verify_layout`/`insideSheet` — et n'est pas branché sur une décision.
   **P-4 d'abord (3 lignes), puis P-1/P-2/P-3.**

   et le registre ont chacun leur « meilleure frame » ; la couche la plus
   récente (registre) a réintroduit la sémantique que B.4 avait corrigée.

   le demi-espace d'inflation jagua et l'absence de plafonds de quantités
   hors démo — deux endroits où « le garde amont » et « la réalité moteur »
   divergent, avec crash ou OOM au bout.
4. **Bugs mirrorés Python↔JS** (P-1, P-2, P-3, Q-1) : la parité
   structureClient/structure est remarquable — y compris dans les bugs.
   Chaque fix se fait symétriquement des deux côtés, avec un test par côté.
5. **État de file du registre** (R-3, R-4, R-5) : la couche la plus jeune de
   l'orchestration locale concentre les états incohérents (annulation non
   câblée, phase non réinitialisée, merge sans garde de survie).
