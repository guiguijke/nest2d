## A. Pass structurel « grille canonique » (SPP)

### A.1 — Bug « demande exacte » : la grille ne se déclenchait jamais

- **Constat** (user, calm-newton 50 Trou + 200 Fillx4) : « le grid n'a pas
  le résultat attendu avec les rectangles en cascade ».
- **Cause racine** : la pré-passe « trous d'abord » (J-085/D-MOT-16)
  extrait TOUTES les petites pièces vers les trous quand la demande est
  exacte (200 = 50 trous × 4) → l'instance de solve réduite ne contient
  plus qu'UNE classe → `detect_structural_case` (exige 2 classes) ne se
  déclenche jamais → aucune alternative grille n'existe. Complément : le
  post-pass `applyHoleFill` aurait de toute façon TÉLÉPORTÉ les fans des
  zones vers les trous vides.
- **Fix** : le pass structurel consomme la **vue ORIGINALE à 2 classes**
  (quantités complètes depuis `payload.parts` + rotations : instance si la
  classe y vit, sinon union des `ringRotations` de la meta pour le filler).
  Nouvel ordre de remplissage : **A → C → trous des hôtes → B** (zones
  internes d'abord = silhouette rectangulaire pleine ; trous = 2e
  réservoir via `expandMeta`/`expand_meta` avec slots recalculés ; B en
  dernier = seule zone qui étend l'axe objectif).
- **Auto-suffisance** : l'alternative structurelle porte les ids
  D'ORIGINE et remplit ses trous elle-même → la finalisation SAUTE pour
  CETTE alternative le remap idMap (corromprait les ids), l'expansion
  meta (doublerait les fillers) et `applyHoleFill` (vidait les zones).
  Drapeaux : `structural: true` + `selfContained: true` (JS) /
  `self_contained` (Python).
- **Fichiers** : `app/composables/localJobPrivate.js`
  (`buildGridAlternative` — vue originale, holePlan, garde anti-perte),
  `app/composables/structureClient.js`, `app/composables/localBridge.js`
  (skip expansions), `workers/nesting/core/structure.py`
  (`build_structural_layout(hole_plan=…)`, `small_lattice`),
  `workers/nesting/core/main.py` (intégration + skips des 2 boucles
  de post-pass).
- **Validation** : e2e THIS DEVICE 50/200 → grille 300,4 mm (2 colonnes
  pleines + 12 reste), zones A=73/C=20 fans, trous=107, B=0, silhouette
  pleine 300,4×2000, bande droite 0,2 % d'encre ; banc worker : `grid`
  rang 0, `overlapFree`/`spacingOk` vrais (250 pièces = limite du garde),
  250/250.

### A.2 — Rectangles successifs (~450 mm) par zone

- **Constat** : zones internes remplies à 38 % (A) et 27 % (C) — bandes
  creuses, pas de « rectangles pleins ».
- **Cause** : banc isolé — le solve plafonne à ~57-60 % de densité sur une
  bande 100 mm ENTIÈRE, indépendamment de la taille, mais tient ~60 %
  PAR TRONÇON de 300-500 mm (49 fans/500 mm ×3 = 147 vs 89 d'un coup).
- **Fix** : `_zone_steps`/`zoneSteps` découpe chaque zone le long de son
  grand axe en pas de `ZONE_STEP_MM = 450` (dernier tronçon ≥150 mm
  fusionné), chaque tronçon rempli ENTIER avant le suivant. Budget ENTIER
  par tronçon (le plateau arrête les runs convergés), abandon sous
  `ZONE_STEP_BREAK = 0,45` du demandé (0,60 tuait des tronçons au
  plafond réel ~0,57).
- **Fichiers** : `structure.py`, `structureClient.js`.
- **Validation** : worker 100/800 : zone A 89 → 120 fans uniformes
  (~10/100 mm sur toute la bande), étendue 684 → 673 mm ; navigateur :
  profil A = 8-12 fans sur chacune des 15 tranches de 100 mm (avant :
  entassées en bas, haut vide).

### A.3 — Lattice analytique des petites pièces (« compression finale »)

- **Constat** (user, captures annotées) : « adaptatif, compression finale
  en direction de l'optimisation » — les lignes 570/655 = largeurs
  physiques cibles des blocs fans, inaccessibles au moteur (plafond 57 %).
- **Fix** : `small_lattice` (Python/shapely+STRtree) et `smallLattice`
  (JS/géométrie pure : `ringDist` sommets↔arêtes, voisins |Δi|,|Δj|≤2) :
  colonnes entrelacées rot0/rot180 (le quart-de-disque s'interpénètre en
  zigzag — pointes fines passant les flancs). Paramètres empiriquement
  validés : `px = W/2 + space`, `py = 1,3554·H`, `dy = −0,378·py`,
  orientation `(i+j)%2`, pièces CENTROÏDE-normalisées (l'ancrage bbox
  casse la phase).
- **Marge de sécurité** : le layout se calcule sur les anneaux SIMPLIFIÉS
  (`NEST_SIMPLIFY_MM`, défaut 0,05) mais le DXF exporté copie les courbes
  BRUTES → validation à `space + 2×LATTICE_SIMPLIFY_MM` sur l'anneau
  simplifié (recalibré sur ring brut : min-dist 0,2 mesuré).
- **Tout-ou-rien par zone** : un top-up moteur dans la même zone
  ÉCRASERAIT le lattice (le solve ne voit pas les pièces déjà posées —
  300 fans dans une zone qui en tient 231, mesuré). Le surplus va aux
  zones suivantes/trous/B.
- **Fichiers** : `structure.py`, `structureClient.js`.
- **Validation** : 100/800 −X worker : grille 67,3 % vs moteur 65,0-65,4 ;
  navigateur : 67,9 % vs 65,6 (A lattice 158 + C 36 + trous 400 + B
  moteur 205 — le lattice vertical perd en bande large : 51 % vs 81 % au
  moteur → B reste au moteur). Vérification exhaustive 900 pièces
  (`bench/verify_grid.py`) : lattice 0 conflit.

### A.4 — Bug JS : placements de la zone B jamais poussés

- **Constat** : 689/900 pièces livrées en rang 0 lors d'un run navigateur.
- **Cause** : le bloc B de `buildStructuralLayout` résolvait puis
  comptait mais oubliait `placements.push(...got)` (l'édition avait perdu
  la ligne ; Python avait bien `placements.extend(got)`).
- **Fix** : push restauré + **garde anti-perte** dans
  `buildGridAlternative` : `placed_items.length !== totalRequested →
  return null` (miroir du part-loss guard serveur `_finalize_alternative`).
- **Fichiers** : `structureClient.js`, `localJobPrivate.js`.

### A.5 — Densité de la grille honnête

- **Constat** : densité grille 1,037 (>1) puis stats trompeuses.
- **Cause** : aire des trous comptée comme matière ; et calcul sur les
  quantités de l'instance réduite.
- **Fix** : densité = aire MATÉRIAU (outer − trous) / bande, calculée sur
  la vue originale. 50/200 → 0,717 (cohérente).
- **Fichiers** : `localJobPrivate.js`, `main.py`.

## B. Bugs du projet démo (BPP multi-tôles)

### B.1 — Test « une seule tôle » sur l'aire NETTE → 3 tôles écrasées en 1

- **Constat** (user) : « le projet de démo est buggé » ; résultat = 1 tôle
  au lieu de 3, ~440 chevauchements réels, pièces hors tôle.
- **Cause racine** : le garde `is_spp` (« tout tient sur une tôle »)
  comparait `total_part_area` = aire **nette** (trous déduits ; démo :
  3,39 m² ≤ 80 % de 4,5) alors que le placement occupe l'aire
  **enveloppe** (4,19 m², ratio 0,93) → mode bande (SPP) forcé à tort
  avec 304 pièces impossibles → chevauchements livrés (les contrôles
  pairwise sont skipés >250 pièces/tôle, garde préexistant).
- **Fix** : `total_outer_area` (anneaux externes) pour le test ;
  `total_part_area` conservé pour densité/journalisation.
- **Fichiers** : `workers/nesting/core/main.py` (~543, ~704),
  `app/composables/localPayloadBuilder.js` (~623, ~641).
- **Validation** : worker journalise `problem_type: bpp`,
  `total_outer_area: 4190149` (ratio 0,93) ; démo → 2 tôles
  (278+26 puis 260+44), 304/304, 0 pièce hors tôle.

### B.2 — Limiteur /api/files 30/min vs 24 géométries/page → 429 en boucle

- **Constat** : 128 erreurs console 429 sur
  `/api/files/project/geometry/demo-marine-lpl-0XX.dxf`, thumbnails
  morts, retries en boucle.
- **Cause** : la page projet consomme UNE géométrie d'affichage PAR
  FICHIER (24 pour la démo) ; le middleware anti-brute-force
  (`5_files_ratelimit.js`, 30 req/min/user sur `/api/files/**`) saturait
  dès le 2e chargement ou un calcul dans la même minute.
- **Fix** : budget séparé 180/min pour `/api/files/project/geometry/`
  (polygones d'affichage, pas des bytes de téléchargement) ; clé de
  compteur suffixée `:geometry`.
- **Fichiers** : `server/middleware/5_files_ratelimit.js`.
- **Validation** : rechargement démo → 0×429.

### B.3 — Champion appliqué au BPP : frame live livrée comme résultat

- **Constat** : la cause directe des 440 chevauchements — le résultat
  livré était une frame EN COURS d'optimisation.
- **Cause** : `preferChampion`/`settleFromChampion` (localPool,
  conçus pour figer un layout SPP convergé via métriques bande)
  remplaçaient le rang 0 du merge moteur par une frame live en BPP
  (métriques nulles → comparaison sans sens).
- **Fix** : `if (!pool.isSpp) return alternatives` (preferChampion) +
  `!pool.isSpp` dans le garde de settleFromChampion. En BPP, le merge
  moteur reste la seule source.
- **Fichiers** : `app/composables/localPool.js`.
- **Signature du symptôme** : layoutCount 1 + usedSheetShare ~1,0 +
  densité nulle sur un job multi-tôles.

### B.4 — Vue live BPP figée (« 1 maj et c'est tout »)

- **Constat** (user) : la vue live fait une mise à jour puis rien
  (instrumentation : 4 updates DOM en 132 s).
- **Causes (2, en cascade)** :
  1. **Rust** : le BPP n'émettait une frame `layout` QUE sur amélioration
     de l'incumbent — fréquent pendant la descente initiale puis
     quasi jamais pendant le plateau (minutes).
  2. **Vue** : `isBetter` (LiveNestingView) ne comparait pas le
     `remnant` (le seul champ qui progresse à bins égaux pendant le
     plateau) et ne remplaçait jamais un champion à qualité égale.
- **Fix** :
  - Rust : le heartbeat SA (1 Hz) embarque le snapshot de l'incumbent —
    `on_heartbeat(usize, &Cost, &BPSolution)`, `layout_event()` factoring
    dans `bpp/mod.rs` ; **wasm rebuildé dans la même PR**
    (bindgen --target web + wasm-opt -O3, hash navigateur vérifié = local).
  - Vue : comparaison `remnant` après `bins` ; à égalité PARFAITE en BPP
    la frame fraîche remplace le champion (rotation entre incumbents des
    walks) ; SPP garde l'incumbent (stabilité du corridor phase 2).
- **Fichiers** : `workers/nesting/engine/crates/nest-engine/src/bpp/sa.rs`,
  `.../bpp/mod.rs`, `app/components/LiveNestingView.vue`.
- **Validation** : ~50 frames/90 s au niveau Worker (hook) ; 867 offres /
  13 changements de layout visibles en 110 s + compteurs animés.
- **Piège cache** : `nest_wasm_bg.wasm` garde le MÊME nom — vider le cache
  HTTP navigateur après rebuild (fetch `cache:'reload'` ou Ctrl+Shift+R),
  sinon l'ancien tourne encore (vérif par hash SHA-256 servi vs local).

### J.1 — Frames live BPP en repère INTERNE (violation 14g, MAJEUR)
- **Constat** : `layout_event` (bpp/mod.rs) sérialisait `pi.d_transf` nu —
  jagua centre chaque pièce au centroïde à l'import
  (`pre_transform`), donc toute pièce non centrée était affichée décalée
  de son centroïde pendant la recherche BPP (le SPP compose via
  `emit_layout`, progress.rs ; l'export final compose via
  `export_layout_snapshot` — seul le live était faux). Défaut préexistant,
  diffusé à 1 Hz par le heartbeat de B.4 (invisible en vérif physique,
  qui ne porte que l'exporté).
- **Fix** : `layout_event` compose `int_to_ext_transformation(d_transf,
  pre_transform)` (signature + instance en paramètre, 2 call sites).
- **Fichiers** : `nest-engine/src/bpp/mod.rs`.
- **Validation** : cargo test + rebuild wasm (hash re-vérifié) +
  `determinism_lock` — cf. §K.

### J.2 — Annulation avalée par le pass structurel
- **Constat** : `EngineCancelled` (sous-classe d'`Exception`, pas
  d'`EngineError`) levé par les sous-solves de zones était attrapé par le
  `except Exception` global du pass grille → job annulé livré + facturé.
  La fenêtre s'était allongée avec A.2 (zones A→C→trous→B en tronçons).
- **Fix** : `except EngineCancelled: raise` avant le `except Exception`
  (nesting/core/main.py) — la finalisation cancelled+refund du solve
  principal s'applique désormais aussi pendant le pass.

### J.3 — Garde anti-panique #2b sur l'aire NETTE
- **Constat** : la garde « strip déflaté » (main.py + miroir
  localPayloadBuilder.js) comparait `total_part_area` (net) alors que
  jagua initialise la bande sur la géométrie réellement posée (≤ aire
  enveloppe) — sous-déclenchement sur pièces très trouées.
- **Fix** : `total_outer_area`/`totalOuterArea` des deux côtés (B.1 avait
  corrigé `is_spp`, pas cette garde-là).

### J.4 — `read_dxf` → None non vérifié (×3 workers)
- **Fix** : gardes + messages actionnables dans fileprocessing
  `_make_dxf_copy`, stripfileprocessing (le dépaquetage explosait en
  `TypeError` avant tout garde — restructuré), nesting
  `get_entities_from_dxf_file` (None empoisonnait aussi le cache doc).

### J.5 — Conversion HATCH non bornée + dépaquetage erroné (×2 copies)
- **Constat** : (a) un HATCH à motif hostile matérialisait des millions de
  segments en RAM (contournement de la limite d'entités → OOM → job figé,
  cf. l'absence de requeue des jobs `processing`) ; (b) `hatch_entity`
  (ezdxf 1.4.4) yield des PAIRES de Vec3 — le `line.start` existant
  levait AttributeError au premier segment de tout HATCH à motif (le
  `raise e` tuait l'import ; passé inaperçu car les HATCH de découpe sont
  presque toujours solid-fill → 0 segment).
- **Fix** : consommation paresseuse bornée à 20 000 segments/HATCH
  (au-delà : HATCH gardé tel quel + warning), dépaquetage correct
  `(start, end)`. fileprocessing + stripfileprocessing.

### J.6 — worker_loop : retries bornés, SIGINT, on_success isolé
- **Fix (worker_common/worker_loop.py)** : (a) re-file falsy compté
  (`processAttempts`, 3 essais max puis erreur actionnable) + backoff
  `idle_sleep` — fin de la boucle chaude possible ; (b) SIGINT traité
  comme SIGTERM (reset du job, plus de `processing` orphelin sur Ctrl+C
  dev) ; (c) `on_success` isolé après l'écriture `done` — un échec Mongo
  transitoire ne requalifie plus un job réussi en error+refund ; (d)
  re-vérification de statut robuste au doc supprimé (`or {}`).
